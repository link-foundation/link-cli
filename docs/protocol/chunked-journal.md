# Optional bounded immutable journal chunks

This is the selected immutable-object strategy at the existing atomic journal
seam. It reduces bytes rewritten for unchanged complete chunks. It does not
change catalog atomicity, journal generations, routing, reader ownership or the
full-journal replay API. Existing `blob1` pointers and objects remain readable;
whole-journal `blob1` writing remains the default.

Select the policy on the existing partitioned store:

```rust
let store = PartitionedJournalStore::new(catalog, partitions, route)?
    .with_chunks(JournalChunkOptions { max_records: 64, max_bytes: 65536, max_chunks: 1024 })?;
```

```csharp
var store = new PartitionedJournalStore(catalog, partitions, route,
    cacheBytes: 0, chunks: new JournalChunkOptions(64, 65536, 1024));
```

```js
const store = new PartitionedJournalStore(catalog, partitions, route,
  { chunks: { maxRecords: 64, maxBytes: 65536, maxChunks: 1024 } });
```

These are the default limits when the policy is explicitly selected; JS accepts
`chunks: {}`, Rust supplies `JournalChunkOptions::default()` and C# supplies
`new JournalChunkOptions()`. Omitting the policy retains whole-journal writes.
The read API and engine/session configuration are unchanged. Object caching is
independent; no cache is allocated at its default zero budget.

The independent write policy specifies positive `maxRecords`, `maxBytes` and
`maxChunks`. Records are split in order, starting a new chunk before a record
would exceed either count or UTF-8 payload-byte budget. Empty records consume
one record; no empty chunk is emitted. A record larger than the byte budget is
rejected. The complete updates and routes must be admitted before any I/O.
All runtimes require well-formed Unicode in selected chunk records. Hard format
bounds are 65,536 records per chunk, 8,388,608 UTF-8 payload bytes per chunk and
4,096 chunks per journal. The write policy may select smaller bounds. Manifest
record totals must fit an unsigned 32-bit integer.

A live catalog journal uses these ordered string records:

```
chunks1, partition, total-records, chunk-count,
object-key, object-generation, object-record-count,
...one triple per ordered chunk
```

Decimal fields are canonical ASCII without leading zeroes. Generations are
nonzero unsigned 64-bit values. Total/count may be zero only together, producing
a live empty journal with four manifest records and no data objects. An absent
catalog generation remains zero with no records. Chunk references use existing
`blob1-` plus sixteen lowercase hexadecimal digits, with the unchanged FNV-1a
64-bit index over `blob1|` and each UTF-8 byte-length-prefixed record. FNV is not
authentication. Staging compares complete actual stored contents, even on a
read-cache hit, and never overwrites a collision. A generation-zero data reply
must have no records.

Validate every selected manifest, configured partition, exact field count,
count sum and hard bound before fetching any data. Referenced objects must have
the exact recorded nonzero generation, record count, hash and format bounds.
Returned records are owned copies. Malformed manifests, missing/modified objects
and unsupported formats fail closed. Older implementations reject `chunks1`;
select it only after upgrading all readers of that namespace.

After every immutable chunk is staged and read back, a single catalog CAS checks
all requested generations, including read-only dependencies. A stale CAS can
leave orphans; a lost response is not retried automatically. Existing verified
object caching may reuse unchanged chunks during reads. Fresh staging still
compares every referenced object's complete contents: staging reads and full
engine replay remain linear. Catalog metadata grows with chunk count, and one
catalog remains the coordination boundary. There is no throughput claim here.

The ordinary append-only partitioned namespace never deletes these objects.
The separately selected epoch-fenced reclamation format is incompatible unless
its complete reference graph is explicitly supported. A collector must reject
an unsupported manifest before deleting any object. Chunk reclamation and its
reader-retirement schedules require separate verification before claiming that
combination.

`chunked-journal-vectors.json` is generated by the independent finite oracle in
`experiments/issue-138/build-chunk-vectors.py`; it covers empty/live-empty data,
count and UTF-8 byte boundaries, BOM, NUL and supplementary-plane characters.
